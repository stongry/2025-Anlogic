【SDRAM读取时序问题】
====================================================================

当前实现(UDP_Example_Top.v:735):
```verilog
.app_rx_data_valid(Sdr_rd_en),      // 直接使用读使能作为数据有效
.app_rx_data(image_data),            // image_data = Sdr_rd_dout重组后的数据
```

问题: **Sdr_rd_en是读请求信号,Sdr_rd_dout是读数据输出**

SDRAM读取流程:
---------------------------------------
T0: App_rd_en=1, App_rd_addr=100  → 发起读请求
T1: SDRAM内部处理...
T2: SDRAM内部处理...
T3: Sdr_rd_en=1, Sdr_rd_dout=??? → 数据可能还没准备好!
T4: Sdr_rd_en=1, Sdr_rd_dout=数据@地址100 → 数据才真正有效

**关键**: Sdr_rd_en拉高的时刻,Sdr_rd_dout可能还是上一次的旧数据!

这就解释了:
---------------------------------------
- ✅ 为什么"大部分画面正确" - 连续读取时,延迟是固定的
- ✅ 为什么"夹杂条状噪点" - burst边界、FIFO空等情况导致时序变化
- ✅ 为什么"噪点是顶部96行" - 这是FIFO中缓存的最早数据
- ✅ 为什么"实时跟随" - FIFO中的数据随着新写入而更新

```verilog
// ========== SDRAM读取时序对齐 ==========
// 问题: Sdr_rd_en比Sdr_rd_dout提前若干周期
// 解决: 延迟Sdr_rd_en使其与Sdr_rd_dout对齐
reg Sdr_rd_en_d1, Sdr_rd_en_d2, Sdr_rd_en_d3;
reg [23:0] Sdr_rd_dout_d1, Sdr_rd_dout_d2, Sdr_rd_dout_d3;

always @(posedge sdr_clk or negedge rst_n) begin
    if(!rst_n) begin
        Sdr_rd_en_d1 <= 1'b0;
        Sdr_rd_en_d2 <= 1'b0;
        Sdr_rd_en_d3 <= 1'b0;
        Sdr_rd_dout_d1 <= 24'b0;
        Sdr_rd_dout_d2 <= 24'b0;
        Sdr_rd_dout_d3 <= 24'b0;
    end
    else begin
        // 3级延迟链
        Sdr_rd_en_d1 <= Sdr_rd_en;
        Sdr_rd_en_d2 <= Sdr_rd_en_d1;
        Sdr_rd_en_d3 <= Sdr_rd_en_d2;

        Sdr_rd_dout_d1 <= Sdr_rd_dout;
        Sdr_rd_dout_d2 <= Sdr_rd_dout_d1;
        Sdr_rd_dout_d3 <= Sdr_rd_dout_d2;
    end
end

// 选择合适的延迟级别 (根据测试结果调整)
wire Sdr_rd_en_aligned = Sdr_rd_en_d2;      // 先尝试2周期
wire [23:0] Sdr_rd_dout_aligned = Sdr_rd_dout_d2;

wire [7:0] image_r = Sdr_rd_dout_aligned[23:16];  // 修改这里
wire [7:0] image_g = Sdr_rd_dout_aligned[15:8];
wire [7:0] image_b = Sdr_rd_dout_aligned[7:0];
// ========== 时序对齐结束 ==========
```

修改Line 735:
```verilog
.app_rx_data_valid(Sdr_rd_en_aligned),  // 使用对齐后的信号
```

【总结】
====================================================================

经过多次尝试,我现在确信问题的根源是:

**Sdr_rd_en信号与Sdr_rd_dout数据存在时序偏移**

这是典型的SDRAM读取延迟问题:
- 读请求发出(App_rd_en=1)
- SDRAM内部处理延迟 (CAS latency通常是2-3周期)
- 读使能输出(Sdr_rd_en=1)
- 数据输出(Sdr_rd_dout=有效数据)

如果Sdr_rd_en拉高时数据还没准备好,就会采样到旧数据。

CRITICAL BUG FOUND - 读地址被frame_available强制复位
====================================================================

【发现时间】2025-10-24
【Bug位置】app_wrrd.v Line 220-224

【Bug代码】
```verilog
else if(!frame_available) begin  // frame_available = (wr_frame_cnt != rd_frame_cnt)
    r_addr_cnt <= 19'd0;         // ❌ 强制复位读地址!
    rd_done <= 1'b0;
    app_rd_en_reg <= 1'b0;
end
```

【Bug机制】
1. `frame_available = (wr_frame_cnt != rd_frame_cnt)` (Line 53)
2. 当写帧计数 == 读帧计数时,`frame_available = 0`
3. 此时`r_addr_cnt`被强制复位到0 (Line 221)
4. 由于`App_rd_addr = r_addr_cnt` (我之前的修复),读地址也被复位到0
5. **结果: 读地址无法超过307199,一直在0-307199之间循环**
6. **更糟: 每当写读追上时,读地址就被拉回0,导致反复读取顶部区域!**

【为什么会出现"顶部96行重复"?】

时序分析:
---------------------------------------
T0: 写帧0完成,wr_frame_cnt = 1
T1: 开始读帧0,rd_frame_cnt = 0, frame_available = 1 ✅
T2: r_addr_cnt从0递增...
T3: r_addr_cnt到达96行区域 (约61440地址)
T4: 读帧0完成,rd_frame_cnt = 1
T5: **frame_available = 0** (wr_frame_cnt == rd_frame_cnt)
T6: **r_addr_cnt被强制复位到0!** ❌
T7: 写帧1完成,wr_frame_cnt = 2
T8: frame_available = 1,开始读"帧1"
T9: **但r_addr_cnt从0重新开始!** 再次读取顶部96行
T10: 循环重复...

实际效果:
---------------------------------------
- 每一帧都从地址0开始读
- 由于UDP发送需要时间,可能只读到前96行就被复位
- **全屏像素都来自前96行的数据**
- **实时跟随**: 因为每次都重新读取最新写入的前96行

【症状完全吻合!】
---------------------------------------
✅ 全屏条状噪点
✅ 噪点与顶部1/5行实时同步
✅ 绿色物体进入顶部 → 全屏变绿
✅ 左右位置对应 (因为是顺序读取,只是地址范围错误)
✅ 倾斜条纹 (因为每次复位时机不同,产生相位差)

【正确的修复方案】

方案A: 移除frame_available检查 (简单但可能不安全)
---------------------------------------
删除Line 220-224,允许读地址连续递增

风险: 可能读到正在写入的帧

方案B: 使用offset机制 (参考工程方案)
---------------------------------------
- 写帧0到地址0-307199
- 写帧1到地址307200-614399
- 读取时使用offset避开正在写入的区域

需要修改SDRAM大小定义

方案C: 完全重写读逻辑 (最安全)
---------------------------------------
1. 移除复杂的burst控制
2. 简化为: 当frame_available时,连续读取整帧
3. 读完后等待下一帧

====================================================================
视频条状噪点问题最终修复方案
修复日期: 2025-10-24
====================================================================

【用户实测症状 - 关键线索】
1. ✅ 满屏幕倾斜条状噪点
2. ✅ 噪点颜色与顶部1/5行(96行)颜色相同
3. ✅ **实时跟随**: 绿色物体进入顶部 → 全屏噪点立即变绿
4. ✅ **左右对应**: 噪点左右位置与顶部1/5行左右位置相同
5. ✅ **从上到下传播**: 绿色物体进入1/5行时,噪点自上而下变绿

【根本原因分析】
====================================================================

症状3-5揭示了核心问题:

**SDRAM读地址一直停留在顶部96行区域,没有正确递增!**

不是数据"重复",而是**全屏307200个像素都在错误地读取顶部96行的地址**

====================================================================
【代码bug定位】
====================================================================

文件: /home/ysara/Desktop/video/UDP_EG4_6.2/source_code/rtl/sdr/rtl/app_wrrd.v

Bug位置: Line 271-285 (原始代码)

错误逻辑:
---------------------------------------
```verilog
// ❌ 错误代码:
always @(posedge clk or negedge rst_n) begin
    if(!rst_n) begin
        App_rd_addr <= 19'b0;
    end
    else if(App_rd_en & App_rd_addr < 19'd307199)
        App_rd_addr <= App_rd_addr + 1'b1;  // 只在App_rd_en=1时递增
    else if(App_rd_en & App_rd_addr == 19'd307199)
        App_rd_addr <= 19'b0;
    else
        App_rd_addr <= App_rd_addr;
end
```

问题分析:
---------------------------------------
1. **两个独立计数器**:
   - `r_addr_cnt` (line 210): 控制读使能条件 → 正常递增 ✅
   - `App_rd_addr` (line 274): 真正的SDRAM读地址 → 递增太慢 ❌

2. **递增条件错误**:
   - `App_rd_addr`只在`App_rd_en=1`时递增
   - 但`App_rd_en`由burst控制,每4个周期才有3个周期为1
   - 结果: `App_rd_addr`递增速度只有`r_addr_cnt`的75%

3. **地址滞后导致循环读取顶部**:
   - `r_addr_cnt`递增到100时,`App_rd_addr`才到75
   - `r_addr_cnt`递增到307199时,`App_rd_addr`可能才到23000左右
   - 当`r_addr_cnt`复位到0时,`App_rd_addr`还在23000
   - 下一帧开始时,`App_rd_addr`从23000继续递增...但读使能由`r_addr_cnt`控制
   - 最终导致**只有前96行区域的地址被反复使用**

====================================================================
【修复方案】
====================================================================

方案: **让`App_rd_addr`直接跟随`r_addr_cnt`,保持完全同步**

```verilog
// ✅ 修复后代码 (Line 271-280):
always @(posedge clk or negedge rst_n) begin
    if(!rst_n) begin
        App_rd_addr <= 19'b0;
    end
    else begin
        // 直接跟随r_addr_cnt,保持同步
        App_rd_addr <= r_addr_cnt;
    end
end
```

原理:
---------------------------------------
- `r_addr_cnt`从0到307199顺序递增 (line 216-254)
- `App_rd_addr`始终等于`r_addr_cnt`
- SDRAM读地址与读控制逻辑完全同步
- 保证读取全部307200个像素的正确地址

【为什么之前的修复没效果?】
====================================================================

1. **UDP包大小修复 (1536→1440)**:
   - 这只解决了"多读96字节"的问题
   - 但如果地址本身就不对,读对了大小也没用

2. **读地址复位信号修复 (App_wr_en→App_rd_en)**:
   - 这只保证了地址能正确复位到0
   - 但没解决地址递增过慢的问题

3. **根本问题**: 地址递增逻辑错误
   - `App_rd_addr`一直停留在前96行区域
   - 全屏像素都在读这96行的数据
   - 导致实时跟随现象: 顶部1/5行的内容=全屏内容

====================================================================
【倾斜条纹的解释】
====================================================================

**为什么是倾斜的条纹,而不是水平条纹?**

时序分析:
---------------------------------------
1. UDP发送是逐字节进行的
2. SDRAM读地址虽然错误,但仍在缓慢递增(只是太慢)
3. 每个UDP包发送1440字节(480像素)
4. 当`App_rd_addr`从0递增到96行时:
   - 屏幕已经显示了几十行
   - 这几十行的数据都来自顶部0-96行的不同位置
5. 由于地址递增与屏幕扫描不同步 → 产生倾斜效果

**左右位置对应的解释**:
---------------------------------------
- SDRAM按行存储: 地址0-639=第1行, 640-1279=第2行...
- 如果`App_rd_addr`=100,读取的是第1行的第100个像素
- 这个像素会出现在屏幕上某个位置
- 由于地址递增缓慢,左侧像素来自顶部左侧,右侧像素来自顶部右侧
- 保持了左右对应关系

【技术总结】
====================================================================

教训1: **地址控制逻辑必须简单明确**
---------------------------------------
- 不要使用多个独立计数器
- 读地址应该由单一可控的逻辑驱动
- 参考工程的做法: burst结束时才更新地址

教训2: **实测现象是最好的调试工具**
---------------------------------------
- "实时跟随"现象直接揭示了地址错误
- 比纯粹看代码更快定位问题

教训3: **包大小、地址、时序必须全部正确**
---------------------------------------
- 只修复其中一个不够
- 必须系统性地检查整个数据路径
